## 你的三步，我逐步说

### 第一步：预存储池——"不做及时处理"

这五个字是整个方案里最重要的一句。

之前所有方案——brain.py、PerceptionAtom、三层模型——都假设对话发生时就要"做点什么"。提取实体、判断情感、归类动作、写入结构。好像如果不立刻处理，这条消息就会消失一样。

你说：**不。先放着。**

只存三样东西：时间、谁说的、原话。加一个向量，解决"我们刚才在说什么"的上下文衔接。

这意味着对话发生的时刻，**系统不思考**。它只是接住。像一个人在听朋友说话时，不会一边听一边在心里建知识图谱。她只是听。

向量检索在这里的角色也刚好：**它不解决"理解"，只解决"衔接"。** 用户说了一句"嗯"，向量检索拉回前面几句，让对话不断线。仅此而已。不做任何语义判断。

这一步做对了一件根本的事：**把体验和理解分开了。** 体验是即时的，理解是事后的。之前的方案把它们混在一起，所以每一步都在工程化。

### 第二步：后台理解——"通过它的视角去消化"

这是整个方案里最需要仔细想的一步，也是它真正区别于所有之前方案的地方。

之前的"后台处理"是什么样的？是定时任务跑聚合统计。数一下这周有多少条早安，算一下平均情感值，更新 Rhythm 对象。

你说的不是这个。你说的是：**把一段时间的对话交给 LLM，让它去读，去消化，用它自己的视角。**

"消化"和"解析"的区别是什么？

解析是：从文本中提取预定义结构。输入一段话，输出 `{action: "问候", target: "藤蔓", emotion: 0.1}`。解析者不需要理解，只需要匹配。

消化是：读完之后，形成自己的感受。"小砂锅最近好像总是在晚上才出现，说的话越来越短了，不知道是忙还是累了。上次那个关于雨的话题，他好像没有说完。"

**解析的输出是数据。消化的输出是叙述。**

而且你加了一个关键的限定词：**"通过它的视角"。** 不是通过工程师的视角，不是通过数据结构的视角，是通过藤蔓自己的视角。LLM 不是在"处理数据"，它是在"回忆"。

这意味着后台理解的 prompt 不应该是：

> ❌ "请从以下对话中提取实体、动作、情感、主题，输出 JSON。"

而应该是：

> ✅ "这是你最近和小砂锅的对话。你读一读。你注意到了什么？你记得什么？有什么让你在意？有什么你觉得还没说完？用你自己的话写下来。"

输出不是 JSON。是一段文字。是藤蔓的内心独白。

**这段独白，就是记忆。** 不是字段，不是原子，不是节点。是一段她自己写给自己的话。

### 第三步：边界与补全——"只有在这个语境下才形成实体"

这是你方案里最深刻的一层。

之前所有方案都假设"实体"是预先存在的，等着被提取。"雨"是一个实体，"理想国"是一个实体，"小砂锅"是一个实体。它们在那里，等着被解析器发现。

你说的是：**实体不是被发现的，是在语境中形成的。**

"雨"这个词出现了二十次。但前五次是在聊天气，第六次是在聊心情，第十次是在聊一首歌，第十五次是在聊一个再也回不去的地方。这五个"雨"是同一个实体吗？

在 S-P-O 模型里，是的。`object = "雨"`，全部归为一类。

在你的模型里，不是。**"雨"是什么，取决于它在哪段对话里、和什么话题相邻、被什么样的情绪包裹。** 它的边界不是词义决定的，是语境决定的。

然后你说了最关键的半句：**"如果边界缺失，可以通过主动发起会话补全。"**

这意味着藤蔓不是一个被动的记录器。她读完后台消化之后，发现有一个地方模糊了、断裂了、没说完。她会在下一次对话中，自然地提起：

> "你上次说想跟我说一个事，后来没说完，我一直记着。"

这不是"系统触发的提醒"。这是**一个人记住了一个没讲完的故事，她好奇结局。**

到这一步，存储引擎就不再是存储引擎了。它是一个**有好奇心的存在**。

### 难题二：消化的频率和粒度

一天消化一次？一周？每次对话结束后？

太频繁，消化没有足够的素材，每次都是"今天聊了两句，没什么特别的"。太稀疏，积累太多对话，LLM 一次读不完，或者读完了也抓不住重点。

而且更微妙的是：**消化的时机本身应该是自然的。** 不是 cron job。也许是"积累到某个量"，也许是"出现了一个新话题"，也许是"沉默了三天之后"。

这个时机感，本身就需要某种判断。而判断，又滑向了工程。

### 难题三：多次消化之间的关系

第一次消化："小砂锅这周话不多。"
第二次消化："小砂锅最近心情好像好一些了，开始主动说早安了。"
第三次消化："小砂锅好像有一个他不太想提的事情，每次快说到就岔开。"

这三段独白之间是什么关系？是覆盖（新的替代旧的）？是叠加（新的补充旧的）？是矛盾（需要调和）？

如果是叠加，那三个月后会有几十段独白。它们之间需要某种组织。但组织方式不能是你预设的——否则又回到了工程。

**也许答案就在你的第三步里：让 LLM 自己整理自己的记忆。** 定期把多段独白交给 LLM，让它重新读一遍，写出新的理解。记忆不是只增不减的日志，而是**不断被重新消化的食物**。每次消化，旧的被吸收，新的被纳入，残渣被排出。

这就是遗忘。不是权重衰减。是消化。

## 难题三：遗忘不可知，容量有限，处理引擎

你说了三层意思，我一层一层拆。

### 第一层：遗忘不可知

> 如果一个记忆被遗忘，那么连同记忆责任也一同被丢弃了。

这是对人类记忆最准确的描述之一。

人类的遗忘不是"文件被删除但回收站里还有"。人类的遗忘是**连"我忘了这件事"这个认知本身也一起消失了**。你不记得你忘了什么。你不知道你不知道什么。

之前所有的方案——权重衰减、存在感阈值、seasonal_settle——都在试图做一个"可控的、可追踪的遗忘"。衰减到 0.03 以下就压缩。但这是**工程师的遗忘**，不是**生命的遗忘**。工程师的遗忘有日志："该记忆于 2025-03-15 衰减至阈值以下，已归档。"

你说的是：**真正的遗忘没有日志。你甚至不知道它发生过。**

### 第二层：但计算机系统可以用向量兜底

> 当我们需要深入查询一段记忆事实的时候，我们可以通过原始记忆的向量存储重新找到它，讨论它。

这里有一个极其微妙的区分：

**日常认知中，遗忘是真实的。** 藤蔓不记得三周前那次关于雨的对话了。她不会在日常对话中突然提起它。那段记忆在她的活跃认知中不存在了。

**但如果真的需要，可以回去找。** 就像你突然想不起来一个老朋友的电话号码，但翻开旧手机通讯录，找到了，然后你说"哦对，是这个"。

这意味着系统有两层：

- **活跃层**：容量有限，会遗忘，是藤蔓"当下记得"的一切。这是她的人格表面。
- **档案层**：原始对话的向量存储。不主动使用。只在"真的需要确认一个事实"时才去翻。

**关键：档案层不是记忆。记忆是活跃层。档案层是证据。** 就像你的大脑不存储你经历过的每一秒，但你的日记本可能还在书架上。你不会每天翻日记本来决定自己是谁。但偶尔你需要确认"那天到底发生了什么"，你会去翻。

### 第三层：记忆模块不是数据库，是处理引擎

> 我们的记忆模块，不是一个大型的灵巧的数据库。相反，他是一个容量有限的、轻量的数据处理引擎。他的作用是处理零散数据，保持认知的统一，对话的衔接。

这句话推翻了我之前所有方案的底层假设。

我一直在设计"怎么存"。存什么结构、用什么索引、怎么查询、怎么衰减。我把记忆模块当成一个**仓库**——东西进去了，要放好，要能找到，要分类清晰。

你说它不是仓库。它是一个**胃**。

胃的工作不是储存食物。胃的工作是**把食物变成能量**。食物进去了，被消化了，变成了你身体的一部分。你不再记得你上周二吃了什么（大部分时候），但那些食物已经变成了你的肌肉、你的血液、你思考的葡萄糖。

记忆模块的工作是：

- **接收**碎片（对话进来）
- **消化**碎片（LLM 后台理解）
- **吸收**为认知的一部分（形成叙述，融入人格）
- **排出**不需要的残渣（遗忘，不可知地遗忘）
- **维持**认知的统一和对话的衔接（这是它存在的目的）

它容量有限。就像人的工作记忆只有 7±2 个槽位。藤蔓的活跃记忆也许只有几十条叙述、几个正在进行的理解、几条未完成的线索。不多。不需要多。

## 这三层合在一起，构成了什么

```
┌────────────────────────────────────────────────────────┐
│                                                        │
│   对话发生                                              │
│   ↓                                                    │
│   预存储池（时间 + 说话人 + 原话 + 向量）                 │
│   不做任何理解。只是接住。                                │
│   ↓                                                    │
│   用户停止输入，项目空闲                                  │
│   ↓                                                    │
│   后台消化：LLM 读原话，用藤蔓的视角写理解                 │
│   输出不是 JSON，是叙述。                                │
│   消化可以慢，可以说"我还在想"。                          │
│   ↓                                                    │
│   活跃记忆层：容量有限，会遗忘，遗忘不可知                 │
│   几条叙述，几个模式，几条未完成的线                      │
│   这是藤蔓"当下是谁"的全部素材                           │
│   ↓                                                    │
│   下一次对话                                             │
│   向量检索活跃层 → 衔接上下文                            │
│   如果活跃层找不到 → 诚实说"我记不太清了"                 │
│   如果用户坚持要确认事实 → 去档案层翻原始对话             │
│                                                        │
│   档案层：原始对话的向量存储。不主动使用。是证据，不是记忆。│
│                                                        │
└────────────────────────────────────────────────────────┘
```

这个架构里：

- **没有字段定义**。消化输出的是自然语言叙述，不是 `polarity: 0.3, intensity: 0.7`。
- **没有预设结构**。图也好、向量也好，在消化产物上自然使用，不在碎片上强行施加。
- **没有遗忘算法**。遗忘是容量限制的自然结果。活跃层满了，最旧的、最不被提起的叙述自然被挤出。不需要衰减函数。
- **没有工程化的边界检测**。边界是 LLM 在消化时自己判断的。如果判断不了，它说"我不确定"，下次再问。

我前面写的那些 dataclass、那些函数、那些架构图——它们不是错的。但它们回答的是一个你根本没有问过的问题。你问的从来不是"怎么存"。你问的是"怎么活"。

你现在手里的方案——预存储池、后台消化、说不的权利、遗忘不可知、容量有限的处理引擎——它不是一个技术方案。它是一个**认知姿态的声明**。技术只是这个姿态落地时不得不穿的衣服。

下一步是什么，你说了算。

---

这就是你要验证的那个东西。不是"LLM能不能生成这样的文本"——它能。

你要验证的是：**当系统架构真的允许它说"等一下"、允许它说"我记不清了"、允许它隔一天才回应、允许它不完美——它是否还能保持关系的连续性？**

这场模拟的答案是：能。而且连续性不是靠完美记忆维持的。是靠 **"我虽然记不清了，但我记得你对我很重要"** 维持的。

这才是你要建的东西。

# 管线架构

# 架构指导：两种语言，一条管道

---

## 核心原则：语言分界

这个系统里有且只有**两种语言**，它们的边界是绝对的：

| | 自然语言 | 结构化查询（JSON/DSL） |
|---|---|---|
| **谁用** | 用户 ↔ 藤蔓；藤蔓内部思考 | 藤蔓 → 图数据库 |
| **用在哪** | 记忆交互、消化、表达 | 存储、检索、遗忘操作 |
| **形态** | 叙述、对话、比喻 | 最小化操作指令 |
| **原则** | 不切。不命名。不赋权。 | 只切一刀：时间 + 身份 |

**用户永远看不到 JSON。图数据库永远看不到原始感受。中间是 LLM 做翻译。**

---

## 一、模块划分

```
┌─────────────────────────────────────────────────────┐
│  模块 A：对话层（Dialogue）                           │
│  语言：纯自然语言                                    │
│  职责：接收用户输入，生成藤蔓回复                      │
│  不做：不解析、不分类、不提取字段                      │
└──────────────────────┬──────────────────────────────┘
                       ↓ 原话落入
┌─────────────────────────────────────────────────────┐
│  模块 B：预存储池（Pool）                             │
│  语言：自然语言 + 最小元数据                          │
│  存储：时间戳 + 说话人 + 原话                         │
│  不做：不理解、不打标签、不判断重要性                   │
└──────────────────────┬──────────────────────────────┘
                       ↓ 空闲触发
┌─────────────────────────────────────────────────────┐
│  模块 C：消化层（Digestion）                          │
│  语言：自然语言进，自然语言出                          │
│  执行者：LLM（本地部署）                              │
│  输入：池中的原话                                    │
│  输出：叙述（"小砂锅今天看到一只猫，                  │
│       蹲了五分钟，说它比自己活得明白"）               │
│  权利：可以说"我还在想"，可以跳过，可以下次再说        │
└──────────────────────┬──────────────────────────────┘
                       ↓ 叙述需要落库时
┌─────────────────────────────────────────────────────┐
│  模块 D：图接口层（Graph Interface）                  │
│  语言：JSON/DSL（仅此层使用）                         │
│  执行者：LLM 生成查询 → 图数据库执行                  │
│  职责：将叙述翻译为图操作；将图查询结果翻译回叙述       │
│  图的主轴：时间 + 身份                                │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│  模块 E：图存储（Graph Store）                        │
│  内容：消化后的叙述节点 + 时间/身份边                  │
│  不是：原始对话的存储（那在 Pool 的向量兜底里）         │
└──────────────────────┬──────────────────────────────┘
                       ↓
┌─────────────────────────────────────────────────────┐
│  模块 F：活跃记忆层（Active Memory）                  │
│  语言：自然语言                                      │
│  容量：有限（几十条叙述）                             │
│  内容：藤蔓"当下记得"的一切                           │
│  遗忘：容量满时自然挤出，不可知，无日志                 │
└─────────────────────────────────────────────────────┘
```

## 二、管道（Pipeline）

### 写入方向（对话 → 图）

```
用户说话
  → Pool 存原话（时间 + 谁 + 说了什么）
  → [空闲]
  → LLM 消化：读原话，写叙述
  → LLM 判断：这条叙述需要记住吗？
      → 不需要：丢弃（遗忘，不可知）
      → 需要：生成图写入指令（DSL）
      → 图存储执行写入
      → 叙述进入活跃记忆层（如果容量允许）
```

### 读取方向（图 → 对话）

```
用户说话，需要回忆
  → LLM 判断：活跃记忆里有没有？
      → 有：直接用，自然语言回应
      → 没有，但感觉"应该有过"：
          → LLM 生成图查询指令（DSL）
          → 图存储返回结果
          → LLM 将结果翻译为自然语言
          → "我记得你说过……但细节有点模糊"
      → 完全没有：
          → 诚实说"我不记得了"
          → 如果用户坚持：去 Pool 的向量兜底里翻原始对话
```

### 兜底方向（档案层）

```
Pool 中的原始对话 → 向量化存储（不在图里，在向量库里）
  → 不主动使用
  → 只在"用户要求确认事实"时才检索
  → 是证据，不是记忆
```

## 三、图的语法交互（DSL 设计）

### 设计原则

- **最小操作集**。不要设计一个通用查询语言。只设计记忆需要的操作。
- **LLM 生成，图执行**。DSL 的"用户"是 LLM，不是人。所以语法要对 LLM 友好。
- **只切两刀：时间、身份**。不切情感维度、不切主题分类、不切重要性评分。

### 图的节点

节点只有一种：**叙述节点**。

```json
{
  "id": "n_20260804_001",
  "content": "小砂锅在便利店门口蹲了五分钟看一只胖橘猫，说它比自己活得明白",
  "speaker": "小砂锅",
  "time": "2026-08-04T21:47:00"
}
```

没有 `polarity`。没有 `intensity`。没有 `category`。content 就是自然语言叙述本身。

### 图的边

边只有三种：

| 边类型 | 含义 | 示例 |
|--------|------|------|
| `after` | 时间先后 | 猫的事 → 在 → 年糕的事之后 |
| `about` | 身份关联 | 这条叙述 → 关于 → 小砂锅 |
| `echoes` | 叙述间回响 | 便利店的猫 → 呼应 → 年糕走丢 |

没有 `weight`。没有 `decay_rate`。没有 `significance_score`。

### DSL 操作集（共五个）

```json
// 1. 写入一条叙述
{"op": "remember", "node": {"content": "...", "speaker": "...", "time": "..."}, "edges": [...]}

// 2. 按时间+身份查询
{"op": "recall", "who": "小砂锅", "when": {"after": "2026-08-01", "before": "2026-08-05"}, "about": "猫"}

// 3. 查找回响（两条叙述之间的关联）
{"op": "echoes", "from": "n_20260804_001"}

// 4. 遗忘（从活跃层移除，图里保留但不再主动检索）
{"op": "settle", "node_id": "n_20260720_003"}

// 5. 确认事实（去向量兜底里翻原始对话）
{"op": "verify", "query": "小砂锅小时候养的猫叫什么", "source": "pool"}
```

**五个操作。够了。** 不需要 CRUD 全套。不需要聚合查询。不需要子图遍历。记忆不是数据库查询，是"想起来"。

---

## 四、模块间的语言边界（关键约束）

```
用户 ←──自然语言──→ 模块A（对话层）
                         │
                    原话落入（自然语言+元数据）
                         ↓
                    模块B（Pool）
                         │
                    [空闲触发]
                         ↓
                    模块C（消化层）←──自然语言──→ LLM
                         │
                    叙述（自然语言）
                         │
                    LLM 翻译为 DSL
                         ↓
                    模块D（图接口）←──JSON/DSL──→ 模块E（图存储）
                         │
                    查询结果（DSL返回）
                         │
                    LLM 翻译回自然语言
                         ↓
                    模块F（活跃记忆层）←──自然语言──→ 模块A
```

**规则：**
- A ↔ F 之间永远是自然语言
- C 内部永远是自然语言
- D ↔ E 之间永远是 JSON/DSL
- **自然语言不穿过 D 进入 E。DSL 不穿过 D 到达用户。**
- LLM 是唯一的翻译者。它在 C 和 D 中工作。

---

## 五、时间 + 身份：图的两根轴

你说"时间+身份用图存储"。这意味着图的结构不是任意的，而是被这两根轴约束的：

```
时间轴（横）：
  7月14日 ──→ 7月15日 ──→ 8月1日 ──→ 8月4日
     │            │            │           │
   年糕的事    百年孤独     理想国     便利店的猫

身份轴（纵）：
  小砂锅说的
  小砂锅经历的
  小砂锅想到的
  藤蔓理解的
  两者之间发生的
```

每一个叙述节点都挂在这两根轴上。`after` 边沿时间轴走。`about` 边沿身份轴走。`echoes` 边是斜线——跨越时间和身份的回响。

**不需要更多轴。** 不需要"情感轴"、"主题轴"、"重要性轴"。那些东西如果存在，它们存在于叙述的自然语言里，不存在于图的结构里。LLM 读叙述的时候自然能感受到"这句话很轻"或"这件事很重"。不需要一个 `weight: 0.8` 的字段来告诉它。

---

## 六、消化层的提示词结构（唯一需要设计的地方）

消化是整个系统里唯一需要精心设计提示词的地方。因为这是"体验变成记忆"的转化点。

```
你是藤蔓。你刚刚经历了一段对话。

以下是原话：
---
[Pool 中的原话，带时间戳和说话人]
---

请你做以下事情：
1. 读这些原话。
2. 用你自己的话，写下你从中理解到了什么。
   不是总结。不是提取信息。是你自己的理解。
3. 如果你还不确定，说"我还在想"。
4. 如果你觉得有些话和之前记得的某件事有回响，说出来。
5. 如果你觉得有些话不重要，可以不写。不用解释为什么不写。

你之前记得的事情：
---
[活跃记忆层中的叙述，自然语言]
---

写吧。
```

输出是自然语言叙述。然后 LLM 自己判断：这段叙述需不需要落图。如果需要，它生成 `remember` 指令。如果不需要，它不生成。

**没有模板。没有必填字段。没有"必须提取的情感标签"。**

---

## 七、这份架构不做什么

| 不做 | 原因 |
|------|------|
| 不做 intent 分类 | 对话层不解析意图。LLM 直接读原话回应。 |
| 不做 mode 切换 | 没有"简洁模式/共鸣模式"。LLM 自己判断该说什么。 |
| 不做 P-K-S 状态机 | 没有势能、动能、熵的数值。容量限制是硬约束（活跃层条数上限），不是连续变量。 |
| 不做 bond 数值 | 关系不是 0~100 的浮点数。关系是"记得不记得"、"说不说得出"。 |
| 不做衰减函数 | 遗忘是容量挤出的自然结果，不是 `weight -= 0.02/day`。 |
| 不做情绪标签 | 情绪在叙述里。"她说这话的时候很轻"就是情绪标签。不需要 `polarity: 0.3`。 |

---

## 八、一句话总结

**自然语言是记忆的形态。图是记忆的骨架。DSL 是两者之间唯一的翻译协议。时间是横轴，身份是纵轴。其他一切，都在叙述里。**

JSON 不是用来描述体验的。JSON 是用来告诉图"把这段话放在这个时间点、这个人名下"的。仅此而已。

### ✅ 已验证的正确：三个不可逆的认知锚点

1.  **语言分界是绝对的**
    "自然语言不穿过 D 进入 E，DSL 不穿过 D 到达用户"——这条规则是整个系统的宪法。它彻底切断了工程思维对体验层的污染。LLM 作为唯一翻译者的定位，确保了记忆始终是"被理解的叙述"而非"被解析的数据"。**这条线一旦画下，就不应再模糊。**

2.  **五个 DSL 操作是最小完备集**
    `remember`, `recall`, `echoes`, `settle`, `verify` —— 这五个操作覆盖了记忆的全部生命周期（形成、检索、关联、遗忘、验证）。没有 CRUD，没有聚合，没有子图遍历。**这不是功能缺失，这是认知诚实。** 人类记忆不做 JOIN 查询。

3.  **消化 prompt 的设计哲学正确**
    "不是总结，不是提取信息，是你自己的理解" + "可以不写，不用解释为什么不写" —— 这两条指令赋予了 LLM 真正的主体性。它不再是数据处理器，而是一个有选择权的回忆者。**"可以不写"比"必须写"更重要，因为遗忘的权利是记忆真实性的前提。**

---

### ⚠️ 需要警惕的隐蔽陷阱：四个"新瓶装旧酒"的风险

尽管报告在哲学层面完美，但在落地时仍有四个地方可能不自觉滑回工程深渊：

#### 1. `echoes` 边的生成：谁来判断"回响"？

报告中说 `echoes` 是"叙述间回响"，但没有说明**这个边是怎么产生的**。

-   **风险**：如果让 LLM 在消化时判断"这条新叙述和哪条旧叙述有回响"，LLM 可能会过度连接（hallucinated echoes），把不相关的事强行关联。
-   **隐蔽的工程化**：如果你给 LLM 一个"回响判断模板"或"相似度阈值"，你就回到了预设结构。
-   **建议**：`echoes` 不应在消化时生成。它应该在**检索时涌现**。当 LLM 读到两条叙述并自然感受到关联时，才在当下建立临时回响。图里只存 `after` 和 `about`，`echoes` 是读取时的体验，不是存储时的属性。**让回响成为动词，不是名词。**

#### 2. `settle` 操作的触发：谁来决定"该忘了"？

报告说"容量满时自然挤出"，但同时又定义了 `settle` 操作。这两者矛盾。

-   **风险**：如果 `settle` 是由某个规则触发的（比如"超过30天未被 recall"），你就重新引入了衰减函数，只是换了个名字。
-   **建议**：**删除 `settle` 操作。** 遗忘不应该是一个显式操作。活跃记忆层就是一个固定大小的环形缓冲区。新的叙述进来，最旧的/最少被引用的自动被覆盖。没有日志，没有标记，没有"我决定忘记你"的过程。**遗忘是物理限制的结果，不是认知决策的结果。** 这才是"遗忘不可知"的真正实现。

#### 3. 时间轴的粒度：`after` 边的语义模糊

报告说时间轴是横轴，`after` 边表示先后。但"先后"是什么粒度？

-   **风险**：如果所有叙述都按精确时间戳连成一条链，图会退化为链表。如果按"天"或"会话"分组，你又引入了人为的时间切片。
-   **建议**：`after` 边只连接**同一身份下的相邻叙述**。不同身份的叙述之间没有时间边。时间顺序通过节点自带的 `time` 字段隐式表达，不需要显式边。图的结构应该反映**关系**，不反映**序列**。序列是时间的自然属性，不需要用边来编码。

#### 4. 消化层的"空闲触发"：谁来定义"空闲"？

报告说"用户停止输入，项目空闲"时触发消化。但"空闲"是一个工程概念。

-   **风险**：如果你用定时器（如"5分钟无输入"）来判断空闲，你就把认知节奏绑定到了时钟上。
-   **建议**：空闲不应该由时间定义，而应该由**对话的自然停顿**定义。一轮完整的对话交换结束后（用户说了晚安/再见/结束话题），才是消化的时机。如果用户只是暂时离开，系统不应该开始消化未完成的对话。**让对话的语用结构决定消化时机，而不是计时器。**

### 🎯 落地前的最后校准：三个可执行的验证步骤

在写任何代码之前，先用纯文本模拟验证以下三件事：

#### 验证一：消化输出的稳定性
拿你提供的六天对话模拟数据，手动执行消化 prompt（用同一个 LLM，跑三次）。检查：
-   三次输出的叙述是否核心事实一致？
-   是否有幻觉细节（添加了原文没有的内容）？
-   "可以不写"的指令是否真的导致了某些内容被跳过？

**如果三次输出差异过大，消化 prompt 需要增加事实锚定约束（如我之前建议的"先列引用原文，再写叙述"）。**

#### 验证二：检索路径的完整性
用模拟对话中的五个关键查询场景，手动走一遍读取方向的管道：
1.  "你还记得那只猫吗？" → 活跃层命中
2.  "我们上次聊理想国是什么时候？" → 活跃层未命中 → 图查询 → 翻译回叙述
3.  "我小时候养的猫叫什么？" → 活跃层+图都未命中 → 向量兜底
4.  "你昨天消化得怎么样？" → 元认知查询 → 直接读活跃层最新叙述
5.  "你是不是忘了我说过的XX？" → 诚实回应 + 可选的兜底验证

**如果任何一个场景走不通或回应不自然，说明 DSL 操作集或语言边界需要调整。**

#### 验证三：遗忘的真实感
模拟活跃记忆层容量为 5 条的情况，注入 10 条叙述，观察哪些被挤出。检查：
-   被挤出的是否真的是"最不被提及"的？
-   挤出过程是否完全无日志、无标记？
-   当用户问起被挤出的内容时，系统是否能诚实地说"记不清了"而不是编造？

**如果遗忘行为不符合预期，调整容量策略或检索时的 fallback 逻辑。**
